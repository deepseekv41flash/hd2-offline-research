# 阶段2 设计：自建联机（co-op）—— 方案、里程碑与验收（2026-11-21）

> 性质：**设计档**（等用户拍板后再开工；本档不含实现）。
> 前置：阶段1（离线单机）已 `✓✓ 实机` 收口（[STAGE1-FINAL](STAGE1-FINAL-2026-11-21.md)）。
> 三态：`✓✓ 实机` / `✓ 离线+数据` / `⚠ 未证` / `✗ 否证`。
> 脱敏：不写公网 IP/Token/账号；服务器代号沿用 A/B（见 [T8d](T8d-HELLFORGE-ANTICHEAT-2026-11-21.md) §9）。

## 0. 一句话结论

阶段2 的目标 = **两名（后续 4 名）玩家在当前零售 build 上，通过自建后端「互相看见 → 入厅 → 进同一局并结算」**，
全程 **不改游戏文件、不注入、EAC 保持开启且真实可达、不连官方服务器**。

**推荐形态：方案A「自建发现层 + 保留 PlayFab 云（Lobby 入厅 / Party-或-Steam 传输）」**。
新增关键认知（[B2B3](B2B3-LOBBY-LOGIN-RECON-2026-11-21.md) §2.8）：HD2 数据面是**双轨**——Steam SDR 优先、
PlayFab 兜底 ⇒ 若双机同 Steam 好友时数据面走 SDR，则阶段2 **不需要任何中继服务器**，工作量集中在发现层与状态一致性。
方案B（HellForge 式替身 PlayFab Lobby/Party DLL + 自建传输）作为**备选/远期**，本阶段只做一个只读的成本判定实验。

## 1. 事实基线（已验证 → 对设计的硬约束）

| 事实 | 三态 | 对阶段2 的含义 |
|---|---|---|
| 游戏自有后端只有 `api.live.prod.thehelldiversgame.com`（我们已用 hosts+研究 CA 全量接管） | ✓✓ | 发现层（登录/大厅/任务）全部由我们提供 |
| `/api/lobby*` 是**带外发现通道**：`PUT` 原样存、`GET` 原样返、`connectionString` 不可伪造 | ✓✓ | 我们只需**转发/存储**，不解析串 |
| **入厅由 PlayFab Lobby（Azure 云）完成**：客机 `PFMultiplayerJoinLobby(connectionString)` 连的是 PlayFab | ✓✓ | 方案A 保留 PlayFab；方案B 必须替换客户端 SDK |
| 对 PlayFab 一律回 `200 {}` → Party 栈在 `ListPartyQosServers` 放弃 | ✓✓ | 「假 PlayFab」不可行（T7 R4） |
| 数据面**双轨**：`steam_transport.cpp`（Steam SDR，优先）与 `playfab_transport`（兜底），日志有 "Falling back to playfab" | ✓ | 决定是否需要中继：SDR 走 Valve，无需我们出带宽 |
| EOS/EAC 是启动硬依赖，必须真实可达 | ✓✓ | 阶段2 不劫持 EOS/EAC；EAC 保持 on |
| 登录体 schema：6 字段（未绑定）/9 字段（绑定），`token` 116 字符；不解析票据 | ✓✓ | 后端同时接受两种 body；身份用 IP/预配置/会话映射 |
| 本机两台服务器出方向仅 3–4 Mbps（A 套餐 5 Mbps/500 GB，B 未确认） | ✓✓ | 只做发现层（HTTP JSON，流量极小）绰绰有余；**不要**用它们做全量中继 |
| HellForge 完整替身成本 ≈1.2 万行（4,414 行 C++ + 7,835 行 C#），且其构建无 EOS | ✓ | 方案B 的可行性参照与风险上限 |

## 2. 方案对比与选择

| 方案 | 做法 | 依赖 | 成本/风险 | 结论 |
|---|---|---|---|---|
| **A. 保留 PlayFab 云**（推荐） | 自建发现层；入厅/Lobby/Party（或 SDR）用官方云 | PlayFab 标题 `974A9` 存活（B8）；EOS/EAC 可达 | **最低**；风险=第三方云哪天关（B8/B10） | **本阶段主方案** |
| B. 替身 PlayFab Lobby+Party（HellForge 路线） | 自写 `PlayFabMultiplayerWin.dll`/`PartyWin.dll` 替身 + 自建后端 + 自建传输 | 需还原 179 个导入的 API 面；当前 build 有 EOS 不可替；GPL 只能读设计 | **高**（≈1.2 万行 + 双机联调 + 跟 build） | 远期备选；本阶段只做 E3 判定实验 |
| C. 找 B10「runtime 关 PlayFab」开关 | 关掉 PlayFab 后走平台层/离线层 | 开关存在性未知（仅静态线索 `disabled playfab in runtime`） | 若存在则可能**大幅简化**（不需要 PlayFab） | 本阶段做 E4 静态检索 |

## 3. 架构（方案A）

```
        ┌────────────── 玩家 A（host） ──────────────┐        ┌──────────── 玩家 B（guest） ─────────────┐
        │ 游戏进程（EAC on）                          │        │ 游戏进程（EAC on）                        │
        │   ├─ /api/* ──hosts+DNS──▶ 自建后端（共享） │◀──────▶│   ├─ /api/* ──hosts+DNS──▶ 同一个后端      │
        │   ├─ EOS/EAC ──▶ 官方云（保持真实可达）      │        │   ├─ EOS/EAC ──▶ 官方云（保持真实可达）    │
        │   └─ 数据面 ─┬─ Steam SDR（优先，Valve 中继）│◀══════▶│   └─ 数据面 ─┬─ Steam SDR（优先）          │
        │              └─ PlayFab Lobby/Party（兜底） │        │              └─ PlayFab Lobby/Party（兜底） │
        └────────────────────────────────────────────┘        └──────────────────────────────────────────┘
                                  ▲
                     自建后端 = 发现层（登录/大厅/成员/任务/战况）
                     一台即可（局域网机器 或 公网轻量机；只跑 HTTP JSON，流量极小）
```

要点：

1. **共享后端只有一台**：两台客户端 hosts 指向同一地址。局域网验证可让 host 机器兼做后端（零公网成本）；
   跨互联网再把后端放到公网机（A/B 都够，见 §6 部署）。
2. **EOS/EAC、PlayFab 一律不劫持**：它们走真实公网；我们只接管 `*.thehelldiversgame.com`。
3. **数据面默认交给游戏自己选**（SDR 优先）；阶段2 **不实现中继**。若 E2 实测证明两机走 Party 且可用，也不影响。
4. **证书**：沿用阶段1 的 CA 机制（研究 CA ≤2 天；或复刻产品 `certs.py` 自签/轮换 + CRL）。两台机器都要装 CA。

## 5. 判定实验（先做，成本低、决定路线）

| # | 实验 | 成本 | 通过判据 | 决定什么 |
|---|---|---|---|---|
| **E1** | PlayFab 标题 `974A9` 存活探测（DNS/HTTPS 状态码，不启动游戏） | 30 min | 状态码/错误体表明标题在线、接受 Steam 实体登录 | B8；方案A 是否成立 |
| **E2** | **双机同 Steam 好友** + 自建发现层 → 抓包判定数据面 | 2–4 h（需第二台机器/账号） | 进同一局；抓包显示数据面走 SDR（3478/3479 + POP relay）还是 Party（DTLS 中继）；记录丢包/延迟 | B1 + 双轨是否成立；是否真的"零中继" |
| **E3** | 当前 build 的 `PartyWin.dll`/`PlayFabMultiplayerWin.dll` 与 Microsoft 公开 SDK 版本一致性（尺寸/哈希/导出表比对） | 1 h（只读） | 一致 → 方案B 的 API 面已知；不一致 → 方案B 成本再升 | 方案B 是否保留为备选 |
| **E4** | B10「disabled playfab in runtime」静态检索（exe 字符串/配置/Lua/命令行） | 1–2 h（只读） | 找到开关 → 可能省掉 PlayFab 依赖（方案C） | 是否存在更省路线 |
| **E5** | QoS 链路观察（`3075` 与 Lobby 顺序），确认能否短路 | 1 h（抓包即可） | 顺序不可跳（T7 已暗示）则确认"保留云"是唯一稳的 | 方案A 的边界 |

**顺序**：E1 → E4（都只读、无风险）→ E2（需用户配合）→ E3（只读）→ 再定 M1 之后路线。

脱敏检查、文档更新。

## 8. 风险、边界与合规

1. **不做**：改游戏文件、注入、代理 EOSSDK、绕过 EAC、连接官方服务器、对外运营。
2. **方案A 的第三方依赖**：PlayFab 标题 `974A9` 若关闭，方案A 失效 → 需 B10（E4）或方案B 兜底。
3. **方案B 的边界**：GPL 只能读设计；替身需自写；每次游戏更新可能重做（HellForge 的代价参照）。
4. **误连官方**：产品必须默认阻断官方后端（[T8c](T8c-EACOFF-PATCH-COST-2026-11-21.md) §7 的 L1–L4 设计）；研究测试亦不连官方。
5. **封号/ToS**：EAC 保持 on、不改客户端、不连官方 ⇒ 风险面与阶段1 相同（阶段1 已实机验证可进任务）。

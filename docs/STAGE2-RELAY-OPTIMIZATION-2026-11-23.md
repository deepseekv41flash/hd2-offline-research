# 中继链路优化：能不能去掉服务器 B？（2026-11-23）

> **一句话结论**：能，而且不需要"在 A 上开别的端口"。今天实测确认**拦的是 TLS SNI（游戏域名）**，
> 不是 IP:443 —— 所以用 **A 自己的 SSH（22）把游戏 TLS 原样送到 A 的回环 443**，就是单跳方案，
> `tools/e2_tunnel.py` **只改一个参数**即可，零配置改动、零证书改动。
>
> 但先说清收益：**延迟只快约 30 ms/请求（~12%）**，真正的收益是**去掉一整台服务器的依赖链**。
> 建议：**今晚复测仍走已验证的 B 路径**，复测通过后再切单跳（验证 10 分钟）。

## 1. 现状链路与它是怎么来的

```
游戏 --(hosts: api.live -> 100.67.88.219)--> 本机 e2_tunnel.py:443
     --(SSH direct-tcpip, 经 B 8.163.50.174)--> B --(TCP)--> A:443 nginx --TLS--> mock 127.0.0.1:8443
```

- 为什么不能直连 A：游戏用 **SNI=api.live.prod.thehelldiversgame.com** 握手，而这个域名 + 非官方 IP
  的组合在**我们这条网络**上被 RST（E2 首次发现，今天复测确认）。
- 为什么当时选 B：B 本来就作为"对方宿主机"存在（A2A 测试），顺手当了隧道出口。**不是技术要求**。
- 志愿者侧不受影响：他们的网络不拦，一直直连 `A:443` —— 优化只发生在我们这一侧。

## 2. 今天的实测（决定性）

### 2.1 拦的是 SNI，不是端口

| 组合（本机→A） | 结果 | 判读 |
|---|---|---|
| `A:443` + SNI=游戏域名 | **Connection reset** (0.11 s) | 游戏域名 SNI 在 443 被 RST |
| `A:888` + 同一 SNI | Timeout (8 s) | 外部不可达（安全组），无信息 |
| `A:80` + 明文 HTTP，`Host: 游戏域名` | **404**（nginx 默认站） | 明文 Host 不被拦，端口可达 |
| `A:443` + `SNI=hyw114514.asia` | **200** (0.115 s) | **中性 SNI 放行** |

⇒ 只要**游戏域名 SNI 不出现在公网线路上**，就能直连 A。隧道（SSH）天然满足；
本地 TLS 终止 + 中性 SNI 也满足。

### 2.2 端口与延迟

| 目标 | RTT |
|---|---|
| A:22 / A:80 / A:443 | 33.8 / 31.0 / 33.4 ms |
| A:888 / 8443 / 8080 / 8888 | **全部 Timeout**（安全组只放 22/80/443） |
| B:22 | 46.4 ms |
| **B→A:443** | **2.1 ms** |

⇒ 两跳比单跳只多约 **15 ms RTT**（本机→B 46 ms vs 本机→A 34 ms + B→A 2 ms）。

### 2.3 单跳 vs 两跳（同一个 `tools/e2_tunnel.py`，只改 `--via`）

| 路径 | TLS 握手 | 总耗时（`GET /health`） |
|---|---|---|
| **单跳**：`--via default --target 127.0.0.1:443` | 0.061–0.118 s | 0.219 / 0.230 s（冷启动 0.704） |
| 两跳：`--via server2 --target 106.52.201.42:443` | 0.075–0.146 s | 0.252 / 0.257 / 0.264 s |

两条路都返回 `200 {"ok":true,…}`，且 A 机 discovery 计数全 0（说明测完状态仍是净空）。

## 3. 方案对比

| # | 方案 | 链路 | 延迟 | 改动量 | 加密 | 判定 |
|---|---|---|---|---|---|---|
| **O1** | **单跳 SSH 隧道**：本机→A:22→A 回环 443 | 1 跳 | ≈A 直连（-30 ms） | **改 1 个参数** | 端到端 TLS + SSH | **立即采用** |
| **O2** | 本机 TLS 前置 + A:443 中性 SNI（nginx `location /hd2/`） | 1 跳，无 SSH | 热连接可做到 1 RTT/请求 | 中（A 加 location + 本机放 leaf + 新工具） | TLS（中性 SNI） | 复测后可选升级 |
| **O3** | mock 本地化 + A 反向代理（A 只做公网入口） | 0 跳（本机 localhost） | 最低 | 大（反向隧道 + A nginx upstream 改指 + 存档本地化） | 视实现 | 与存档系统一起做时再议 |
| **O4** | A:80 明文 HTTP 转发 | 1 跳 | 低 | 小 | ❌ 明文 | **不推荐**（`connectionString`/session 明文出网） |
| — | 保留现状（经 B） | 2 跳 | 基线 | 0 | ✅ | 今晚复测用这个（已验证两轮） |

**关于"挪到 A 上别的端口"**：A 的外部可达端口只有 **22 / 80 / 443**（888/8443/8080/8888 全部 timeout）。
所以"别的端口"要先改安全组；而 **22 已经够用**（SSH 隧道），443 也已够用（中性 SNI），
**不需要新开端口**——这正是 O1 的取巧点：用 22 当传输、目标仍是 A 的回环 443，
游戏 TLS 端到端不变，B 直接下线。

## 4. O1 落地（零配置改动）

```bash
# 现在（两跳，经 B）
python tools/e2_tunnel.py --servers-json <servers.json> --via server2 \
  --listen-host 100.67.88.219 --listen-port 443 --target 106.52.201.42:443

# 单跳（经 A 自己的 SSH；目标写 A 的回环，而不是公网 IP）
python tools/e2_tunnel.py --servers-json <servers.json> --via default \
  --listen-host 100.67.88.219 --listen-port 443 --target 127.0.0.1:443
```

- 其余全不变：hosts 仍指 `100.67.88.219`、本机 CRL 仍在 18081、研究 CA 仍要装、游戏仍走端到端 TLS。
- 切换验证（1 分钟）：`curl -k --noproxy '*' --resolve <域名>:443:100.67.88.219 https://<域名>/health`
  → `200 {"ok":true}`；`/health` 的 `discovery` 计数应与切换前一致。
- 回滚：把 `--via`/`--target` 换回 B 的两跳命令即可（两条命令都留在作业单里）。
- 顺带收益：B 不再参与游戏链路（B 内存紧、还跑着其它实验），A 只多一条 SSH 会话。

### 4.1 更稳的运行方式（可选）

`e2_tunnel.py` 是 paramiko 进程，进程挂了游戏就断。可以换成系统 OpenSSH 的本地转发，
交给 Windows 计划任务/服务托管，断线自动重连：

```powershell
ssh -N -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes `
    -L 100.67.88.219:443:127.0.0.1:443 <A 的用户>@106.52.201.42
```

（`-L` 的转发语义与 e2_tunnel 的 direct-tcpip 相同：每条连接在 A 上再向 `127.0.0.1:443` 建一条 TCP。）

## 5. O2 细化（复测后的可选升级，不急着做）

做法：本机跑一个"TLS 前置"，游戏看到的是本地证书（研究 CA 签、SAN=游戏域名），
前置再把请求以 **中性 SNI** 的 HTTPS 发到 A 的 nginx，由 nginx 的一个 location 转给 mock：

```
游戏 --TLS(研究 CA)--> 本机 front:443 --TLS(SNI=hyw114514.asia)/hd2/--> A:443 nginx --> mock
```

需要 3 件事：
1. A 的 `hyw114514.asia` vhost 加 `location /hd2/ { proxy_pass https://127.0.0.1:8443/; }`（一行级改动）；
2. 本机放一份 **A 的 leaf 证书 + 私钥**（`state/certs-a/front/`，随证书轮换一起更新；只在本机，gitignore）；
3. 一个约 100–150 行的 `tools/local_front.py`（TLS 终止 + 上游 keep-alive + 路径前缀转发 + 并发）。

预期收益：**每个请求不再付一次跨洋 TLS 握手**（游戏↔本地前置的握手≈0 RTT，前置↔A 复用热连接），
按 E3 的请求节奏（~0.4 req/s、短连接）估算单请求可从 ~250 ms 降到 ~40 ms；
并且**彻底摆脱 SSH 进程**（无隧道、无 paramiko、无常驻会话）。

代价/风险：多一个进程 + 一份本机私钥；nginx 改动要重启/重载（影响 A 上其它站点，需在维护窗口做）。

## 6. O3（与本项目后续方向的关系，先记录不实施）

如果将来把 **mock 整体搬到本机**（存档系统天然适合本地：0 网络、无 A 依赖），A 只做公网入口：
A 的 443(game SNI) vhost → `proxy_pass` 到我们发起的反向隧道（如 `ssh -R`）→ 本机 mock。
那时我们的游戏请求 0 跳，志愿者的流量经 A 转发。代价：**我们掉线 = 志愿者断**（但测试期我们本来必须在场），
且 A 的 nginx upstream 需要改指隧道端口。→ 等存档系统（S1）落地时再一起评估。

- O1 已实测可用（§2.3），作为**复测通过后的第一步优化**：切换 + 1 分钟验证 + 回滚命令都写好了。

## 8. 不要再做的事

1. **不要开 A 的新端口**：22/80/443 已够；开新端口要动腾讯云安全组，收益为零。
2. **不要用 A:80 明文**：`connectionString`（PlayFab 凭据）、session、公钥都会明文出网。
3. **不要在复测前改 A 的 nginx**：O2 需要 reload nginx（A 上还有别的站点）。
4. **不要指望"换个端口就能直连"**：拦截是 SNI 维度，端口换了 SNI 没变，一样会被 RST
   （除非端口不在拦截策略覆盖内——但 A 的其它端口根本不通，无法验证）。

## 9. 补充实测（2026-11-23 14:50）：换网络 / 目的地矩阵 / Clash 代理

### 9.1 目的地矩阵（同一「游戏域名 SNI」，只换目的 IP:443）

| 目的 IP | 结果 |
|---|---|
| 官方 API（DoH 解析 `68.154.14.134` / 本地 DNS `68.154.15.59`，Azure 美国） | **TLS 握手 OK**（建连 ~280 ms） |
| 阿里 DNS `223.5.5.5` | **OK**（5 ms / 11 ms） |
| 腾讯 DNSPod `119.29.29.29`、百度 DNS `180.76.76.76`、`1.1.1.1` | **Timeout**（目标本身不通） |
| **我们的 A `106.52.201.42`** | **RST**（ClientHello 后约 25–30 ms，即约 1 RTT） |
| 从 **B 机** → A:443 + 游戏 SNI | **TLS 握手 OK**（12 ms） |

⇒ 过滤发生在**我们这条出口链路**上，且**按目的地**区分；A 的服务端完全正常（B 直连可用）。
本机没有 TUN/加速器虚拟网卡，只有 Clash Verge 服务在跑 ⇒ 不是本机加速器驱动在拦。

### 9.2 走 Clash Verge 代理会不会被拦？——**默认规则下会**

实测（`curl -x http://127.0.0.1:7897 --connect-to <域名>:443:106.52.201.42:443`，即强制代理转发到 A、SNI 仍是游戏域名）：

| 路径 | 结果 |
|---|---|
| 经 Clash（强制目标=A） | `schannel: failed to receive handshake`，**0.06 s 失败** |
| 直连（对照） | `Connection was reset`，0.08 s 失败 |

原因不是 Clash 不工作，而是**规则**：当前 profile 是 `mode: rule`，规则尾部为
`- GEOIP,CN,DIRECT` / `- MATCH,<代理组>` ⇒ A 是国内 IP，命中 **DIRECT**，
Clash 只是替你把字节发出去，TLS ClientHello（含游戏 SNI）依旧走在**同一条被过滤的出口**上。

**另外**：游戏进程**不读 Windows 系统代理**（阶段1 已实测），所以对游戏而言 Clash 系统代理
根本不参与——"开代理让游戏连上"这条路本身不成立。

要让 Clash 真正绕过，只有一条路：把 `106.52.201.42`（或 `DOMAIN-SUFFIX,thehelldiversgame.com`）
规则指到**境外节点**——SNI 被封进 Clash 隧道，本地过滤器看不见。但代价是
「本机 → 境外节点 → 腾讯云境内」绕地球，延迟从 **33 ms** 变成 **300 ms 以上**，
且依赖节点稳定性。对比现有 SSH 隧道只多 **~30 ms** ⇒ **不作为方案**。

### 9.3 能否在运营商控制台关掉这条过滤？

- 家宽/校园网自助控制台**没有**「SNI/域名过滤」这类开关（只有拨号、账单、改密、端口映射、
  家长控制等）；这类过滤在**出口安全设备**上，属单位/运营商策略，个人无权改。
- 从 §9.1 的证据看，也**不像运营商统一策略**：官方 IP（美国）与阿里 DNS 都放行、
  只有指向我们自建服务器的组合被 RST ⇒ 更像"游戏域名 + 目的地"的分流/防私服策略。
  要定位到具体设备，最短路径是：换手机热点对照 + 问网管要出口策略（只读排查，10 分钟）。
- **风险判断**：关掉这条过滤在技术上不会让你主机更不安全，但它存在的目的是**阻断
  「官方域名被指向第三方服务器」**（防私服/防中间人截票据）。我们做实验正是靠这条策略
  被绕开的同一手法（改 hosts + 装研究 CA）——**保持它开着反而更安全**。
  我们真正的安全面是「研究 CA 装在根存储」这件事，缓解措施见阶段2 部署档
  （CurrentUser 非 LocalMachine、2 天有效期、实验后卸载、CA 私钥签完即删、只在官方不可达时启用）。

## 10. 实测：自定义规则 + 境外节点绕行（2026-11-23 15:05）——**能绕过过滤，但去不了我们的服务器**

做法：*不动用户现有 Clash*，用同一个 `verge-mihomo.exe` 起**临时第二实例**
（mixed-port 7898、独立控制器、独立配置目录），配置只放 3 个境外节点 + 一条
`IP-CIDR,<A>/32,OUT,no-resolve` 规则；测完自动杀进程、删临时目录（配置含节点凭据，不落仓库）。

### 10.1 结果：TLS 不再被 RST，但落点是**官方服务器**

| 测试（经节点） | 目的地 | 客户端 SNI | 结果 |
|---|---|---|---|
| T1 | `A:443` | 游戏域名 | TLS **成功**，但证书是**官方 Let's Encrypt（YR2）**、`Server: Kestrel`、404/CL:0 ⇒ **是官方 API，不是我们的 A** |
| P1 | **阿里 DNS `223.5.5.5:443`** | 游戏域名 | **仍然是官方 Kestrel** ⇒ 与目的地完全无关，是**按域名接管** |
| P2 | `A:443`（`sniffer: {enable:false}` 显式关闭） | 游戏域名 | 仍然官方 ⇒ **不是 mihomo 在改写目标** |
| T2 | `A:443` | 随机域名 | 到达 **A 的 nginx**（默认站 404）⇒ 节点→A 的通路本身没问题 |
| T3 | `A:80`（明文） | `Host: 游戏域名` | `301` + `Server: Microsoft-Azure-Application-Gateway/v2` ⇒ **明文 Host 也被接管** |
| 对照 | `A:443` 直连 | 游戏域名 | **RST**（本地出口过滤） |

**三个不同节点（香港|IEPL / 新加坡1 / 美国1｜高速）行为完全一致**，
且把 SNI=游戏域名打到「阿里 DNS 的 IP」也拿到官方后端 —— 说明是该**代理服务商**在
出方向上按域名接管 HD2 API 流量（典型的"游戏加速/智能路由"行为），不是我们本地、不是 A 机、也不是 mihomo。

### 10.2 延迟（经节点，`/health` 一次往返）

| 节点 | 总耗时（3 次均值） | TLS 握手 |
|---|---|---|
| 香港\|IEPL | **1030 ms** | 701 ms |
| 日本1 | 1298 ms | 891 ms |
| 新加坡1 | 2499 ms | 1706 ms |
| **对照：SSH 隧道（经 B / 经 A 的 22）** | **220–300 ms** | 60–150 ms |

⇒ 即使不看"落点是官方"这个致命问题，境外绕行的延迟也是隧道的 **4–10 倍**。

### 10.3 结论

1. **境外节点确实绕过了本地 SNI 过滤**（TLS 不再 RST）—— 这反证了 §2 的判断：
   过滤在我们这条出口链路上，且只针对「游戏域名」。
2. **但它到不了我们自己的服务器**：该服务商按域名把 HD2 API 流量接管到**官方后端**。
   所以「自定义规则 + 境外节点」这条路**不能用于私服链路**。
3. 延迟 4–10 倍、还依赖第三方节点 ⇒ 即使能到也不划算。
4. **仍然用 SSH 隧道**：端到端 TLS 封在隧道里，任何"按域名分流/接管"的设备都**看不见 SNI**，
   这是它相对代理方案的本质优势（延迟也只有 +30 ms）。
5. ⚠ **副作用提醒**：这类"游戏加速"型代理会按域名接管流量 —— 以后**测私服时不要同时开着它**
   （否则游戏可能悄悄连到官方而不是我们的 A，现象会和"连不上"很像，极难排查）。

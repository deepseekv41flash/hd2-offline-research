# 可分发的"SNI 拦截"绕过方案（早期设计，2026-11-23）

> ## ⛔ 状态：留档（ARCHIVED-PLAN）—— 本研究线**不实施**，留待产品化
>
> **决策（2026-11-23，用户明确）**：分发给"可能被 SNI 拦截的他人"属于**产品化阶段**的问题。
> 研究线当前目标是把阶段2 双人协作收口，**继续沿用「两端自有机器 + SSH 隧道」**。
>
> - **为什么现在不做**：现状只服务"我们自己的两台机器"，不需要对第三方分发；
>   一旦分发就要背"工具信任 + 证书分发 + 令牌运维 + 合规"四件事，与阶段2 收口无关。
> - **什么时候重新拾起**（任一满足）：
>   ① 需要给非自有机器/第三方玩家接入；② 有玩家侧出现同类 SNI 拦截且无法换网络；③ 产品化立项。
> - **已完成的前置（不用重推）**：自有域名从被拦网络可达（实测 200/401）；
>   A 机 nginx 已有 `map $http_upgrade` + 12 处 WebSocket 反代先例；我们自己就是被拦网络，可先本机验收。
> - 索引与其它移交项见：`PRODUCTIZATION-BACKLOG-2026-11-23.md`（B1/B2/B4）。

> **要解决的问题**：现在 SSH 隧道能跑，是因为两端机器都是我们的。如果**别人**（志愿者/其他玩家）
> 也处在一个会按「游戏域名 SNI」拦截的网络上，我们不能把 SSH 凭据给他 —— 那等于给一台服务器的
> 登录面。需要一个**凭据不外借、权限只到一条窄口子**的分发方案。
>
> 本文只做设计与取舍（不改代码）。全部方案都基于今天实测的三条事实：
> ① 拦的是「游戏域名 SNI → 非官方目的地」；② 我们自有域名（`*.hyw114514.asia`）从被拦网络
> **可以正常 TLS 访问**（实测 200/401）；③ 商业加速/VPN 会**按域名劫持** HD2 流量到官方后端（§10
> 已实测，不能用）。

## 0. 一页速览

| 项 | 结论 |
|---|---|
| 推荐方案 | **R1：玩家侧"字节隧道客户端" + 我们域名下的 WSS 隧道端点（每玩家一个可撤销令牌）** |
| 玩家拿到什么 | 一个 URL + 一个令牌 + 一个可回滚安装脚本；**没有任何服务器凭据/SSH/证书私钥** |
| 加密模型 | 外层：我们域名 TLS（Let's Encrypt）；内层：**游戏 TLS 端到端不变**（研究 CA 签的服务器证书） |
| 玩家机器上的信任变化 | 和现在一样（只需研究 CA 来信任游戏服务器证书）；**不需要**游戏域名的证书/私钥 |
| 服务器改动 | 新增一个 systemd 小服务（127.0.0.1:18443）+ 一个 nginx vhost（`hd2.hyw114514.asia`）；**不开新端口**（复用 443） |
| 工作量 | 约 **2.5 人日**（服务端 0.5 / 客户端 1 / 套件与文档 0.5 / 端到端验收 0.5） |
| 最大好处 | **我们自己就是"被拦网络"**，整条链路能在本机先验收，再分发给别人 |

## 1. 硬性安全要求（不满足就不做）

1. 不向玩家分发任何能登录我们服务器的凭据（SSH key/密码/面板账号）。
2. 玩家侧**不做 TLS 中间人**：不在玩家机器上生成/保存游戏域名的证书私钥；游戏到 A 的 TLS 保持端到端。
3. 隧道端点**只允许一个目的地**（A 的 127.0.0.1:443 = 发现层 nginx），不能变成通用代理。
4. 凭据（令牌）**可按玩家单独撤销**、有连接数与带宽上限、可审计（只记元数据）。
5. 玩家侧全部动作**可一键回滚**（停客户端、删 hosts 行、卸 CA、删令牌文件）。
6. 不碰游戏文件/内存 → 与阶段1/2 同 EAC 风险等级（低）。

## 2. 为什么不用商业 VPN / 加速器

今天已实测（`STAGE2-RELAY-OPTIMIZATION-2026-11-23.md` §10）：经三家不同境外节点，
游戏域名流量**被按域名接管到官方后端**（官方 Let's Encrypt 证书 + `Server: Kestrel`），
且与目的地无关。⇒ 商业代理对"自建服务器"这条路**不可用**，还会让玩家悄悄连回官方服。
另外，让玩家装第三方代理本身也过不了第 1 条（把他的全部流量交给第三方）。

## 3. 方案对比

| # | 方案 | 玩家拿到什么 | 权限范围 | 撤销 | 客户端代码 | 判定 |
|---|---|---|---|---|---|---|
| **R1** | **WSS 字节隧道**（推荐） | URL + 令牌 | 仅"到 A 的 443"这一条字节流 | 删令牌即断 | 需一个小工具（或复用 wstunnel） | ✅ |
| R2 | 受限 SSH 隧道账号 | SSH key + 账号 | `permitopen=127.0.0.1:443`、`command=/bin/false`、no-pty | 删 key | **不需自研**（用系统自带 ssh.exe） | ⚠ 备选：仍是"给账号"，SSH 登录面暴露；用户明确担心这点 |
| R3 | 商业 VPN / 加速器 | 第三方客户端 | 全部流量 | 玩家自己 | 无 | ❌ 实测被按域名劫持；且违背"不把流量交第三方" |
| R4 | 换网络（手机热点等） | — | — | — | 无 | 兜底话术，不可规模化 |

**R2 的价值**：零自研客户端，标准 OpenSSH 限制足够严（`authorized_keys` 加
`restrict,command="/bin/false",permitopen="127.0.0.1:443",no-pty,no-agent-forwarding,no-x11-forwarding`，
sshd 侧 `Match User hd2tunnel*` 再限）。如果 R1 来不及，可先用 R2 顶一轮；但长期不推荐（理由见 §6 对比表）。

## 4. 推荐方案 R1 详设

### 4.1 架构

```
玩家游戏 --(hosts: 游戏域名 -> 127.0.0.1)--> 玩家侧 hd2-front（只听 127.0.0.1:443）
      │  ① 每条 TCP 连接：先做"直连探测"，直连能通就直接转发到 A:443（不绕）
      │  ② 直连被拦：开 WSS ──TLS(SNI=hd2.hyw114514.asia, LE 证书)──> A:443 nginx
      │                                                        └─ location=/tunnel → 127.0.0.1:18443 hd2-tunnel
      │                                                            └─ 校验令牌 → 固定连 127.0.0.1:443（发现层 nginx）
      └─ 游戏↔A 的游戏 TLS **端到端**（研究 CA 证书，玩家装一次 CA —— 与今天相同）
```

要点：**外层 TLS 在 A 的 nginx 终止**（我们自己的机器，可接受）；**内层游戏 TLS 不被任何人终止**。
玩家机器上不出现游戏域名证书私钥 → 没有客户端 MITM。

### 4.2 服务端组件（A 机）

| 组件 | 说明 |
|---|---|
| `hd2-tunnel`（新，小服务） | 监听 `127.0.0.1:18443`；WSS 握手后校验令牌 → 连接**固定** `127.0.0.1:443` → 双向字节转发；每令牌连接数/带宽上限；只记元数据日志 |
| nginx vhost `hd2.hyw114514.asia` | 只暴露 `location = /tunnel`（WebSocket upgrade 反代到 18443），其余 404；复用 443，**不开新端口** |
| 令牌库 `state/tunnel/tokens.json` | `{id, sha256(token), note, conns, mbps, created, revoked}`；`mockctl tunnel issue/revoke/list` 管理 |
| systemd `hd2-tunnel.service` | 与 `hd2-discovery` 同风格（Restart=always、专用用户、只读根） |

nginx 配置草稿（新子域，独立 vhost，不动现有站点）：

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name hd2.hyw114514.asia;
    ssl_certificate     /www/server/panel/vhost/cert/hd2-tunnel/fullchain.pem;
    ssl_certificate_key /www/server/panel/vhost/cert/hd2-tunnel/privkey.pem;

    location = /tunnel {                    # 唯一入口
        proxy_pass http://127.0.0.1:18443;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;   # 复用已有的 map
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        client_max_body_size 0;
    }
    location / { return 404; }
}
```

> A 机 nginx 已有 `map $http_upgrade $connection_upgrade` 和 12 处 WebSocket 反代先例（DSH 等），
> 这是成熟路径，不引入新机制。

### 4.3 客户端（玩家侧，两种形态二选一）

| 形态 | 优点 | 缺点 |
|---|---|---|
| **A. 自研单文件 exe（Go 编）** | 可审计、无运行时依赖、可用 `curl` 一样验收 | 需要构建与签名/校验和分发 |
| **B. 复用现成 `wstunnel`** | 不写代码、成熟 | 多一个第三方二进制（需信任 + 校验和），参数面更大 |

客户端职责（两形态都一样）：
1. 监听 `127.0.0.1:443`（hosts 把游戏域名指到这里；Windows 上绑定环回 443 不需要管理员）；
2. 对每条连接：**直连探测**（对 A:443 用游戏 SNI 做一次 TLS 握手，1–3 s 超时）
   - 通 → 直接 TCP 转发到 A:443（不经过隧道，零额外延迟）；
   - 不通（被拦）→ 建立 WSS 隧道，按字节透传；
3. 令牌从 `token.txt` 读（不入日志）；支持 `--endpoint` 覆盖；
4. 失败要给出可读原因（直连被 reset / WSS 401 / nginx 404 等）。

### 4.4 玩家侧操作（4 步 + 一键回滚）

```powershell
# 1) 装研究 CA（仅用于信任游戏服务器证书；与现在的 kit 相同）
certutil -user -addstore Root ca.cer
# 2) 改 hosts 指向本机（而不是 A 的 IP）
#    游戏域名 127.0.0.1 api.live.prod.thehelldiversgame.com # HD2-TUNNEL
# 3) 起客户端（前台窗口，显示 直连/隧道 模式）
hd2-front.exe --endpoint wss://hd2.hyw114514.asia/tunnel --token-file token.txt
# 4) 验收
curl.exe --noproxy "*" -k --resolve api.live.prod.thehelldiversgame.com:443:127.0.0.1 `
  https://api.live.prod.thehelldiversgame.com/health     # 期望 200 {"ok":true,...}
# 回滚（一条命令）
uninstall-front.ps1     # 停客户端 → 删 hosts 行 → 卸 CA → 删 token.txt
```

### 4.5 验收判据（全部可先在我们自己机器上做，因为我们就是"被拦网络"）

| 阶段 | 判据 |
|---|---|
| 服务端单测 | 令牌校验/撤销/上限/固定目的地；不合法令牌必须 401 且不建连 |
| 本机端到端 | 本机直连 A:443 被 RST（已知），客户端自动切隧道 → `curl /health` **200 mock JSON**；A 机日志出现真实请求 |
| 反向对照 | 直连可用的网络（如从 B 机）→ 客户端应选择直连、A 日志无隧道连接 |
| 游戏级 | 装 kit 后游戏能进主界面、能进厅（与阶段2 现有验收同口径） |
| 撤销 | A 侧 `revoke` 后，玩家新连接立即失败；重开令牌即恢复 |
| 回滚 | `uninstall-front.ps1` 后 hosts/CA/进程全部复原 |

## 5. 安全分析

### 5.1 权限对比：为什么它比"给 SSH"安全

| 维度 | 给受限 SSH 账号 | R1 令牌隧道 |
|---|---|---|
| 玩家持有物 | SSH 私钥（能向服务器认证） | 随机令牌（只能开隧道） |
| 可做什么 | 只能 `permitopen=127.0.0.1:443`，但仍需**登录** sshd | 只能往 127.0.0.1:443 转发字节 |
| 服务器暴露面 | sshd 认证面（爆破/凭据填充/协议漏洞都在这一面） | 443 上一个 WSS location + 一个本机端口 |
| 撤销 | 删 authorized_keys（要动 sshd 配置面） | 令牌库置 revoked（不碰系统认证） |
| 审计 | sshd 日志 | 隧道服务日志（连接数/字节/时长，无载荷） |
| 最坏后果（令牌/私钥泄露） | 有人能登服务器（受限但仍登录） | 有人能往游戏端口打流量（限速、可撤销、重启即换） |

### 5.2 攻击面与缓解

| 风险 | 缓解 |
|---|---|
| 令牌外泄 | 每玩家独立令牌 + 连接/带宽上限 + 可撤销 + 每次测试可轮换；令牌只存哈希 |
| 玩家拿隧道当通用代理 | 服务端**硬编码**目的地 `127.0.0.1:443`，不解析任何目标地址参数 |
| 大流量/借道 | 单令牌并发与带宽上限；nginx `limit_req`/`limit_conn`；异常即吊销 |
| 端点被扫/被滥用 | 只有 `/tunnel` 一个路径，其余 404；无令牌一律 401；按 IP 限速 |
| 客户端木马嫌疑 | 提供源码 + 校验和 + 只出站到我们域名、只监听 127.0.0.1；明确"不做系统级改动，除 hosts（可回滚）" |
| 玩家机器上的 CA 风险 | 只装研究 CA（`CurrentUser`、2 天、可卸）；**不做**游戏域名证书 ⇒ 比"客户端 MITM"方案少一大块风险 |
| 合规 | 文档写明：绕过其网络过滤可能违反该网络使用规定，建议先申请或换网络；我们只提供"到自有测试服务器"的最小通路 |

## 6. 与其它工作流的关系

- **今晚复测**：不依赖本方案（我们自己的 SSH 隧道继续用），本方案是"分发给他人"的长期件。

## 8. 需要拍板的 5 件事

1. **子域名与证书**：用新子域 `hd2.hyw114514.asia`（要加 DNS 记录 + Let's Encrypt 证书，隔离最干净）
   还是先挂在现有 vhost 的一个 location 上（省事但混用）？**建议前者**。
2. **客户端形态**：自研单文件 exe（可审计）还是集成 `wstunnel`（少写码但多一个第三方二进制）？**建议自研 Go 单文件**。
3. **令牌粒度**：每玩家一个令牌（推荐）还是共享一个（省事但无法单独撤销）？
4. **外部玩家的 CA 策略**：继续用 2 天研究 CA（每次测试都要重装，摩擦大）还是为"外部玩家"单独签一个
   30 天测试 CA（降低摩擦、但放宽安全面）？
5. **是否同时支持"直连优先、失败回退"**（推荐）：网络不拦的玩家零额外延迟；被拦的自动走隧道。
